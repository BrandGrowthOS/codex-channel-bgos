A picture a Codex agent makes now appears in the chat by itself

Ask a Codex agent for a banner and today it makes one, says it is done, and the picture never reaches the chat unless the model remembers to attach it. After this change the picture posts itself when the agent's turn finishes, first in the reply, with the words it was made from as its caption (Prompt: ...). It opens in the viewer and shows in the gallery and in Artifacts like any other picture. Codex only. Always on, nothing to switch on. The app itself does not change.

What stays the same

Claude Code and every other agent. Nothing changes for them. Claude Code has no picture item of its own; a picture it makes with a tool reaches the chat the way it does today, when the agent attaches it.
A picture the agent attaches itself. MEDIA: lines and the reply tool's files still work exactly as before. If the agent attaches the very picture that already posted itself, that line is dropped, so you never get it twice.
Nothing to switch on. No setting, no per agent toggle, and the technical details switch does not affect it: the picture is a normal message, visible with the switch on or off.
The tool card. The image_generation row reads the same as today. The picture is a message beside the card, not a row inside it.
The app. No app UI code changes. The picture goes through the same path as any picture an agent sends: the chat, the viewer, the gallery, Artifacts, on desktop and both phones.
Your repo. No file is written into the agent's working folder. The picture's bytes go straight up from the plugin; Codex's own copy stays where Codex keeps it.

06

Decisions I took, what the agent is told, and two things I saw

Decisions I took (the ledger has the reasons)
  1. Codex only. Claude Code has no picture item, so there is nothing to catch there.
  2. At the end of the turn, first in the reply. A post mid turn marks the agent done for the rest of the turn: the working line, the Stop button and the stall catchers all go off. A stopped turn and an adopted goal turn still post the pictures they finished.
  3. The bytes, not a file. The picture's bytes are decoded (capped at the 10 MB image limit) and uploaded straight from the plugin, so no file lands in your repo and the media guard keeps its one root.
  4. One post per picture, caption "Prompt: ..." clipped, and any em or en dash in the model's prompt becomes a comma so nothing you see carries one. A refused picture gives one plain line naming the reset time.
  5. One sentence in the capability guide, for Codex only, served to daemons at 0.13.0 or later (version suffix -images1), mirrored in the doc and the sync test; the same sentence in the plugin's own hints.
  6. No app change. Agent pictures already render in the chat, the viewer, the gallery and Artifacts. A small app PR carries the sentence, the floor and the What's New card, and merges after the plugin release is out.
  7. One live probe on this machine's Codex to record the real picture shape, as a modest spend of the kind P2's probes made. It ran and could not make a picture: this box's Codex is not logged in (a 401 before the model). The shape was read from the runtime binary instead, and the code accepts bare base64 or a data URI and does not depend on the status words.
What the agent is told
One sentence, in the capability guide a Codex agent reads on connect (daemons at 0.13.0 or later) and in the plugin's own hints:

A picture you make posts itself to the chat when the turn finishes, with its prompt. Do not send it again with MEDIA:.

The ledger's wording; a plugin test pins the final words and the no dash rule.
Two things I saw in the app (not caused by this change)

The viewer shows the file name, never the prompt. Open the picture and the strip at the bottom reads the file's name; the caption stays in the chat. Whatever name the plugin picks is what you read there, so the plugin names the file codex-image-<id>.png rather than Codex's exec-<uuid>.png. Showing the prompt there is an app change for another day.

Technical detail (for the build)
  1. Where: the Codex plugin, branch feat/p5-image-posts, version 0.13.0, stacked on P2's feat/p2-file-diffs (a6a5c3a, 0.12.0). Merge order #12, #14, #15, then this. The map was written at 99a6ed7; every anchor below was re-checked on the branch head.
  2. The seam, host side (src/codex-host.ts): a REQUIRED images map on ActiveTurn, so the compiler forces both constructors (execute() and adoptTurn()) to initialise it. On item/completed of an imageGeneration item the picture is collected by item.id (the dedupe: a second completion for the same id does not add) and the branch falls through so the tool row still builds. result(), the one constructor for turn/completed and the watchdog, carries images, so a timed out turn keeps its pictures. When an owner turn takes over an adopted goal turn, prior.images is read before release() and seeded into the new turn.
  3. The pure half (src/generated-images.ts): decodeImageResult (bare base64 or a data: URI, MIME sniffed from the bytes, refused over IMAGE_BYTES_MAX 10 MB before allocating), collectGeneratedImage (bytes, prompt, savedPath, never the base64; null without an id; an exec- id collects the same as an ig_ one), imageCaption ("Prompt: ..." clipped on a word boundary at IMAGE_CAPTION_PROMPT_MAX, dashes to commas, folded onto one line, none without a prompt), imageFailureLine (the one line, reset time in UTC, seconds or milliseconds, none without a time, a plain fallback for an unknown kind).
  4. The post, adapter side (src/adapter.ts, publishTurnResult): pictures FIRST, then the body, buttons or ask branch, then the MEDIA: loop, then finalizeTurn. The error early return posts the pictures before finalizeTurn and sendAgentError. The Stop branch posts finished pictures after progressWork and before finalizeTurn, with no text, no refusal line and no red error. The fallback guard counts SUCCESSFUL posts (postedImages === 0), because each post is caught. A MEDIA: path whose real path equals a posted picture's savedPath is dropped; it is kept when that picture's own post failed. Refused pictures post one line per limit.
  5. Outbound (src/outbound.ts, src/attachment-bridge.ts): sendImageBytes mirroring sendFile so deliver() retry (1 s, 5 s, 25 s) and the spool apply; publishMediaBuffer exported over the private publishMediaBytes (inline data URI under 500 KB, presigned PUT above; 120 s timeout). The media guard is untouched.
  6. Canon and hints: a Codex sentence constant in backend/src/integrations/capability-canon.ts gated by a floor at 0.13.0 (never ahead of the code, capability-canon.version-gate.spec.ts), CAPABILITY_CANON_VERSION suffix -images1, the markdown mirror and the sync spec both ways; src/agent-hints.ts one line; test/capabilities.spec.ts pins it word for word with the no dash assertion. LATEST_PLUGIN_VERSIONS.codex bump and the What's New card ride the same small app PR.
  7. Tests, RED first, one suite at a time (--minWorkers=1 --maxWorkers=4): test/generated-images.spec.ts (the pure half), test/adapter-image-posts.spec.ts (the decision guard: the post's call order is after host.runTurn resolved and before reply.sendText, and posting from a mid turn callback turns it red; image before an ask and before buttons; no fallback when a picture posted with no text; the fallback when every post failed; the refusal line; the error early return; the Stop branch; the adopted deliver path), test/codex-host.spec.ts (collected once, deduped, started alone adds nothing, failure carried, the watchdog result, the adopted hand over), test/outbound-media.spec.ts (bytes path, 10 MB cap), test/activity-markers.spec.ts (the row reads savedPath). Two zero cost stub runs showed a legacy image_generation_call is silently dropped by the runtime and the image tool is not offered without a ChatGPT login.
